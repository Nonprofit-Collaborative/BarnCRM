## Scale test

### Import: 25,000-row file on tier 1 (2026-10-28)

The last open run of the tier 1 scale test, at the pilot bar of 25,000 rows (D-90). Passed:
the import completed with no failed rows, and undo of the whole batch completed.

**Org and volumes.** `oi-test` (scratch org, 500 MB data storage), from `main` at 52909176.
Background data loaded with `scripts/org/scale-test-tier1.sh oi-test` and
`SCALE_TEST_GENERATOR_ARGS="--gifts 15000"`: 4,000 households, 10,000 contacts, 15,000 gifts,
15,750 allocations, 31,365 soft credits (1,500 from the file, the rest automatic household
member credits), no failed rows; storage 498 MB free before, 343 MB after. Gifts were halved
from 30,000 so the import's own records (about 180 MB) fit in the 500 MB org. Contact and
household volumes, which the import's matching runs against, are the full tier 1 figures.

**File and path.** `scale-test-data/import-wizard-25k.csv`: 25,000 gift rows from 8,333
donors (3 gifts each, matched by email), "Generic gift list" template with its suggested
mapping unchanged (all 8 columns mapped), matching rule Email exact, payment matching "Match
or create", fund "Scale test General". Driven headlessly through the wizard's own
`ImportController` calls, one anonymous Apex transaction per call, in the wizard's order:
`getTemplates`, `suggestMapping`, `createBatch` (no stored file: the file is 2.54 MB, over the
wizard's 2.5 MB keep limit, so the wizard also sends none), `stageRows` in 50 pages of 500 rows
in file order, `startDryRun`, `startCommit`, `previewUndo`, `startUndo`. Each page went to the
org as a ContentVersion that the transaction read, because anonymous Apex refuses a script
that size. Chunk size 200 (the default).

| Step | Elapsed | Rate | Jobs | Result |
| ---- | ------- | ---- | ---- | ------ |
| Stage rows (50 calls of 500) | 247 s | | | 25,000 rows staged; time is mostly CLI round trips, not the org |

| Undo (`ImportUndoBatch`) | 584 s (17:56:31 to 18:06:15 UTC) | | 18 jobs, 704 of 704 items, 0 failed; 304 `RollupQueue` and 250 `RollupLargeParentBatch` jobs alongside, 0 errors | Status Undone: "33333 records deleted, 0 kept, 0 values put back" |

The commit created 8,333 contacts, 8,333 households (one per new person), 25,000 gifts and
25,000 default allocations; no soft credits (single-member households). The undo removed all
of them: record counts returned exactly to the pre-import figures.

**Largest chunk against its limit** (from the debug log of every chunk, asynchronous limits):

| ----- | --- | ------------ | ---------- | -------- | ---- |
| `ImportProcessorBatch` (commit) | 1,428 of 60,000 ms (2%) | 23 of 200 | 1,479 of 50,000 | 603 of 10,000 | 407 KB |
| `ImportUndoBatch` | 1,985 of 60,000 ms (3%) | 15 of 200 | 700 of 50,000 | 103 of 10,000 | not logged |
| `RollupQueue` (during undo) | 1,228 of 60,000 ms (2%) | 16 of 200 | 1,521 of 50,000 | 200 of 10,000 | not logged |

No chunk came near 70% of any limit. The dry run's chunks wrote no limit block at the trace
level used, so they are not in the table; the dry run had no failed items.

**Error Log.** 0 rows created during the import, the dry run, the commit or the undo. Four
`RollupQueue` warnings appeared later, during the tier 1 cleanup (deleting the loaded gifts,
contacts and households, not the import): 169, 5, 30 and 41 records' totals waiting for a
retry. The Rollup Queue was empty afterwards.

**Findings.**

- None at or over 70% of a limit; no failed rows; no product defect found.
- Observation, not a defect: the undo preview and the run log count only records the import
  tagged (8,333 people and 25,000 gifts, total 33,333). The 8,333 households created
  automatically for the new people and the 25,000 default allocations were also removed (the
  allocations with their gifts), so the undo
  deleted about 66,700 records while the confirmation shows 33,333. Worth a line in the import
  admin guide if administrators read the confirmation total as everything removed.
- Test setup gap (fixed in the test plan): the org test gate no longer assigns permission
  sets, so the CLI user had no field access to `Gift__c.External_Id__c` and the load script
  stopped at its existing-data check. The run assigned `Giving_Admin` to the CLI user and
  removed it afterwards.

**Extrapolation.** At about 4,240 rows a minute, a 250,000-row file would commit in about an
hour on a scratch org (1,250 chunks, well inside the daily asynchronous limit), with undo at
about 10 minutes per 25,000 rows, its follow-on rollups included. The 250k run stays a tier 2 sandbox
run (D-90).

**Cleanup.** `scale-test-tier1.sh cleanup oi-test` removed the scale households, contacts,
gifts, allocations, soft credits and the five non-default funds (soft delete: the CLI user has
no Bulk API Hard Delete permission). The run also deleted its staged `Import_Row__c` rows, the
import batch record and the 50 page files. `oi-test` is back to the sample data counts (226
accounts, 440 contacts, 0 gifts); the generated default fund "Scale test General" stays, as
the cleanup keeps a configured default fund by design, and the wizard materialized its
shipped templates.
