# C-12 permission requirements

What the guided Setup Assistant needs in each packaged permission set, on top of what
`c-03.permissions.md` already lists. C-12 ships no permission set files: the integrator
merges these entries into `Nonprofit_Admin`, `Nonprofit_Staff`, and `Nonprofit_Read_Only`.

The assistant runs the same permission gate as the settings console: reading is open to
everyone who can open the Hub, and every save checks the `Manage_Nonprofit_Settings` custom
permission (created by C-04) through `FeatureManagement.checkPermission`.

## Nonprofit_Admin

| Kind | Entry | Why |
|---|---|---|
| Apex class | `SetupAssistantController` | Every panel of the assistant calls it. |
| Apex class | `ModuleDetectionService` | Step six asks it what is installed. |
| Field | `Setup_Steps_Skipped__c` on `Nonprofit_Settings__c` | Read and Edit: a skipped step is remembered. |
| Field | `Setup_Started_At__c` on `Nonprofit_Settings__c` | Read and Edit: how long setup took. |
| Field | `Organization_Legal_Name__c`, `Organization_Address__c` on `Nonprofit_Settings__c` | Read: the organization step and the Organization section of the settings console. |
| Object | `ContentDocument`, `ContentVersion`, `ContentDocumentLink` | Create and Read: a File field a module adds to a step uploads a file. Standard file access, no extra object. |
| Object | `User` | Read: step four picks a person with a record picker. |

## Nonprofit_Staff

| Kind | Entry | Why |
|---|---|---|
| Apex class | `SetupAssistantController`, `ModuleDetectionService` | The assistant has to load; saving is refused by the permission check, not by class access. |
| Field | every `Nonprofit_Settings__c` field above | Read only. David reads how the org is set up and cannot change it. |
| Object | `ContentDocument`, `ContentVersion` | Read only: the upload controls are not rendered without the permission. |

## Nonprofit_Read_Only

Same as `Nonprofit_Staff`, with nothing writable anywhere.

## Notes for the integrator

- **Custom permission gate.** `SetupAssistantController` checks `Manage_Nonprofit_Settings`
  on `completeStep`, `skipStep`, `reset`, `applyCoexistence`, `saveStepValues`, and
  `assignAccess`. `getState` is open, so David sees the same steps with a notice naming the
  permission he is missing. (C-29, ADR-0059: `saveStepValues` replaced
  `saveOrganizationIdentity` and `saveDefaults`, and accepts only the keys the step declares.)
- **The custom permission, not field level security, governs saving.** Every step value goes
  through `SettingsService`, which writes the settings object in system mode through
  `SettingsWriter` after re-checking `Manage_Nonprofit_Settings` (ADR-0006, ADR-0017), so the
  settings fields need no edit access in any permission set.
- **Superseded by C-29 (ADR-0059).** The fund and appeal step, the tax identification number,
  the receipt logo, signature and signer fields, and the first-gift button are Giving's: they
  are declared by `GivingSetupAssistantExtension` and saved on `Giving_Settings__c`, and the
  Giving permission sets and the Giving tabs govern them. Core names none of them.
- **Uploads.** Step five uses `lightning-file-upload`, which requires a record to attach the
  file to. There is no record a logo belongs to, so it attaches to the current user's own
  record and only the `ContentDocumentId` is stored in settings. Standard file permissions
  therefore apply, and the file belongs to whoever uploaded it. The admin guide says so.
- **Components the assistant renders, owned by other features.** Core panels are imported by
  name, literally, and a module's own screen is reached by navigation (ADR-0020). None of
  these is on this branch; each one degrades to a notice that says why:
  - `c/householdNamingSettings` (C-02), step two. Absent: the step shows the naming notice
    and completes when `Household_Name_Pattern__c` gets a value some other way.
  - `c/sampleDataManager` (C-10), step seven. Absent: the sample data notice.
  - The Giving package's gift entry tab, step eight. Since C-29 (ADR-0059) Giving declares
    the button itself, through `GivingSetupAssistantExtension`, so Core no longer names the
    tab; without Giving the step has no button.
- **Settings fields the completion rules read**, both owned by other features. A step whose
  field does not exist never completes by itself; it still completes when Maria finishes it:
  - `Nonprofit_Settings__c.Coexistence_Mode__c` (C-07), the completion key for step one.
  - `Nonprofit_Settings__c.Household_Name_Pattern__c` (C-02), the completion key for step
    two. `SetupAssistantServiceTest` writes it, so that test needs C-02's field to exist.
- **Integration points this branch stubbed rather than shipped**, all owned by other
  features. Each one is called defensively (a failure costs the panel its data, not the
  page), except the two marked required:
  - `ErrorLogger.log(Exception, String)` (C-05).
  - `OrgShapeDetector.detect()` returning `OrgShape` with `hasPersonAccounts`, `hasNpsp`,
    and `hasIndustriesNonprofit` (C-07 and C-11). Step one degrades to the fresh org case if
    it throws.
  - `CoexistenceService.getCurrentMode()` and **`CoexistenceService.applyMode(String)`**
    (C-07, required). `applyMode` is the one method C-12 needs that the brief did not list:
    confirming a mode has to put that mode in force, and `applyRecommendedIfUnset()` cannot
    express "Maria chose a different one". C-07 owns the implementation.
  - `AccessService.getRoles()` returning role developer names, and
    `AccessService.assignRole(Id, String)` (C-06, required for step four). The assistant
    renders each developer name with its underscores replaced by spaces; when C-06 ships
    labelled roles, step four should use those labels instead.
- **Setting Definition rows.** C-12 ships seven rows in a new **Organization** section of the
  settings console, so everything step five writes is also editable later on the settings
  page. `Default_Fund__c` and `Default_Appeal__c` deliberately have no rows, and are written
  with `SettingsService.saveSystemValue` rather than the definition-validated path, for two
  reasons: a Core row would render a bare record identifier in the console, which plan
  Section 2.3 forbids, and a row in a **Giving** section shipped by Core would appear on
  Core-only orgs where there is no fund to choose. Giving ships those rows, with a picker
  panel, in v0.2 when Fund and Appeal exist. The write is not unvalidated in the meantime:
  `saveDefaults` refuses an identifier whose object is not the fund or appeal object that
  describe reports, so a default can never point at a Contact or a User. Superseded by C-29
  (ADR-0059): the default fund and appeal, the tax identification number and the receipt
  fields moved to `Giving_Settings__c` with rows shipped by Giving, and `saveStepValues`
  checks a record field against the object the step declares.
- **Unprefixed tab links.** `setupAssistant.js` links to `/lightning/n/Import` and to the
  settings page, and `setupStepFields.js` navigates to the tab a step's Navigate field names
  (Giving's `Gift_Entry`, declared by Giving); `hubHome.js` links to
  `/lightning/o/Error_Log__c/list`. None of these carries a namespace today. They are
  revisited when a namespace is assigned (Decision D-01).
- **Open question for the receipt work (G-13, G-14).** The logo and signature are uploaded
  with `lightning-file-upload` against the uploader's own user record, so the
  `ContentDocumentLink` it creates governs who can read the file. Before a receipt render
  reads that file as another user, the visibility that link is created with has to be
  verified and, if it is private to the uploader, an Apex-created link with
  `ShareType = 'V'` and `Visibility = 'InternalUsers'` added. This is recorded here rather
  than solved on this branch because the receipt render does not exist yet.
